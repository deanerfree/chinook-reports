# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Phoenix LiveView app for authoring and viewing oil & gas well drilling reports ("Chinook Reports"). Reports can be created manually through a multi-step wizard or generated by uploading a client's Excel workbook, which a Python side-script parses into JSON. Elixir/Postgres persist and serve everything; LiveSvelte embeds a few interactive charts.

## Commands

```bash
mix setup              # deps.get + ecto.setup (create/migrate/seed) + assets.setup + assets.build
mix phx.server          # run the app (localhost:4000); iex -S mix phx.server for a REPL
mix test                # creates/migrates the test DB, then runs the suite
mix test path/to_test.exs:42   # single test at a line
mix ecto.reset          # drop + recreate + migrate + seed
mix ecto.gen.migration add_some_column   # new migration in priv/repo/migrations
mix credo               # static analysis (dev/test only)
mix dialyzer            # type checking (dev/test only)
mix format              # respects .formatter.exs (imports ecto/ecto_sql/phoenix formatting, HEEx plugin)
```

Assets: `live_svelte`/`phoenix_vite` (Node 19+) build the Svelte components under `assets/svelte/`; `mix assets.build` / `assets.deploy` run both Tailwind and `npm run build` in `assets/`.

Excel extraction requires `python3` on PATH — it shells out to `priv/scripts/python/extract_all.py` (see Architecture below). There's no dependency manifest for it visible in-repo; check `priv/scripts/python/` for what it imports before assuming a package is available.

## Architecture

### Two data representations on one schema

`ChinookReports.Reports.Report` (`lib/chinook_reports/reports/report.ex`) is the only schema, but a report's data lives in two very different places:

- **Typed columns + `report_data` embed** — filled in by the manual creation wizard (`CreateReportLive`). `report_data` is an `embeds_one` with nested `embeds_many` lists (`profile_sections`, `formation_tops`, `surveys`). This is the "structured" path.
- **`import_data` (a raw, untyped map)** — populated wholesale by `HandleData.store_report_data/1` when a report comes from Excel upload or JSON seeding (`test/test_data/*.json`). Its top-level keys (`welldata`, `tops`, `reservoir_data`, `synopsis`, `daily`, `mud_log`, `bits`, ...) are extraction-script output, read with `get_in`/pattern matching rather than a schema. Most of the report-page UI (`ReportSummary`, `FormationTopsLive`, `ReservoirQualityLive`) reads and edits *this* side.

A report can carry both — the wizard's typed fields plus imported JSON — so don't assume one implies the absence of the other.

`Reports.ensure_report_data/1` must be called before building an edit changeset for any report that might have come in via import (its `report_data` embed may be a struct with `id: nil`, which crashes Ecto's embed diffing on update otherwise).

### The `Reports` context is the only door to `Repo`

LiveViews and components never touch `ChinookReports.Repo` or `Reports.Report` directly (`ChinookReports.GenServer` is the one exception — see below). `Reports.update_import_section/3` is the standard way to persist a change to one top-level key of `import_data` without touching the others.

### Derived data lives in dedicated modules, not in the schema or the views

Several `import_data` sections have calculated columns that must never drift from their inputs. Each has one module owning the recompute, called from every place that can invalidate it:

- **`ChinookReports.FormationTops`** — recomputes `import_data["tops"]` (TVD/subsea/isopach/diff per formation, per group: prognosis/samples/mwd_gamma) against the directional survey and KB elevation. Triggered by editing the tops table itself, editing Elevations (KB change ripples through), or a survey update. Rows beyond the current survey reach are extrapolated and flagged `provisional?/1`.
- **`ChinookReports.ReservoirQuality`** — recomputes a reservoir leg's `quality_summary` (metres/percent per quality band) whenever its `intervals` are edited via the Reservoir Quality picker (a Svelte drag-to-classify UI, not a form).
- **`ChinookReports.Survey`** — recomputes an imported directional survey's TVD/N-S/E-W/VS/DLS/subsea and its `markers` after its stations are edited, from the first changed station down (rows above it keep the extractor's values). A survey or KB edit saves the tops it re-derives in the same update via `FormationTops.with_tops/2` + `Reports.update_import_sections/3`.
- **`ChinookReports.Trajectory`** — minimum-curvature integration of survey stations (MD/inclination/azimuth) into TVD/N/E/vertical-section, used to plot the planned trajectory against the actual one.
- **`ChinookReports.ReportSummary`** — the read-only view model for the report page's Summary tab; folds `import_data` into header/tabs/facts/reservoir-quality/depths/timeline/synopsis/chart props. Fully nil-safe (a report with no `import_data` still renders, with empty sections).

When editing anything that feeds one of these (KB elevation, a survey point, an interval list), check whether the edit path already re-invokes the relevant recompute — `ReportPageLive.handle_event("save_section", ...)` re-derives tops after an elevations save, for example.

### `ChinookReports.Reports.Editing`

Shared add-row/remove-row logic for `report_data`'s `embeds_many` lists, used identically by the create/edit wizard and the report page's inline editors. Exists because `Ecto.Changeset.put_embed/3` on an already-modified `report_data` struct doesn't reliably register nested list changes — see the comment on `put_in_report_data/3` before changing this pattern.

### Excel import pipeline

`UploadLive` → `ChinookReports.GenServer` (a singleton `GenServer`, registered in the supervision tree, also used to serialize `fetch_report`/`fetch_reports_list` calls) → `ChinookReports.ExcelExtractor` → spawns `priv/scripts/python/extract_all.py` as a `Port`, streaming `PROGRESS:<step>` lines back as extraction-progress messages → `HandleData.store_report_data/1` decodes the resulting JSON and upserts a `Report` (`on_conflict: :replace_all, conflict_target: :unique_well_id` — re-uploading the same well replaces its report). The Python extractors live one-per-section under `priv/scripts/python/extractors/`.

### The create/edit wizard (`CreateReportLive`)

A single LiveView drives both create and edit (`/create_report` vs `/reports/:id/draft`). Steps, per-step mandatory fields, and which steps are `embeds_many` table steps are all declared as module attributes at the top of the file (`@steps`, `@mandatory`, `@list_steps`) — extend those rather than adding parallel conditionals. `Report.changeset/2` also reassembles split date/time HTML inputs (`<field>_date` + `<field>_time`) into one datetime string before casting; see `merge_split_datetime_fields/1` if adding another datetime field to a form.

### Report page (`ReportPageLive`)

Tab-based; the active tab is kept in the URL (`?tab=`) so a refresh doesn't snap back to Summary. Sections are edited inline (`editing` assign holds which section's form is open) except Formation Tops (its own `LiveComponent`, `FormationTopsLive`, which persists itself and notifies the parent via `send(self(), {:tops_updated, report})`) and Reservoir Quality (a Svelte picker that pushes a `commit_intervals` event on every change — there is no explicit save).

### Dates

`spud_date`, `final_td_date`, and `profile_sections[].start_date` are `:naive_datetime` (wellsite local time, entered and stored with no timezone conversion) — not `:date`. See the `convert_dates_to_datetimes` migration for the history; a bare `"YYYY-MM-DD"` string is still accepted on import and defaults to midnight (`HandleData.parse_datetime/1`).
